# Known limitations

(Each entry: what, why, workaround.)

- **No sidebar vibrancy (NSVisualEffectView).** Why: real vibrancy needs a transparent window
  (`transparent: true`) plus translucent `--bg-sidebar` tokens in `src/index.css`; with today's opaque
  tokens it would be invisible and only cost compositing. Workaround: the window background is set to
  the sidebar colour per appearance (menu.rs), so there is no white flash. To enable later: set
  `transparent: true` on the window, apply `Effect::Sidebar` via `window.set_effects`, and make the
  sidebar background translucent in Tauri only.

- **Artifacts — CDN dependencies.** React/Tailwind/Mermaid previews and npm imports load from esm.sh / jsDelivr (pinned versions), so those kinds need network access; Markdown/CSV/JSON/SVG/code/plain HTML render offline. Workaround: write plain HTML artifacts for offline use. See docs/ARTIFACTS.md §5.
- **Artifacts — shadcn/ui imports.** Only a subset of `@/components/ui/*` (button, card, input, textarea, label, badge, alert, separator, progress, switch, checkbox, slider, tabs, select, table) is shimmed with lightweight Tailwind components; other components fail with a clear error. Workaround: the agent builds them inline or ships `components/ui/<name>.tsx` in the artifact.
- **Artifacts — web storage.** `localStorage`/IndexedDB on the custom `artifact://` scheme may be unavailable or non-persistent in WKWebView. Workaround: keep artifact state in memory.
- **Artifacts — old versions in the browser build.** Previewing/reading version snapshots needs the desktop app (Rust reads them from disk); in plain-browser dev only the live version is shown.
- **Runtime — browser dev mode (no Tauri).** Without the Rust side there are no conversation sandboxes, file listing, uploads folder, project knowledge copies, opencode.json writes or settings.json: chats use the server's default directory, attachments are sent as data URIs (text files inlined), settings live in `localStorage`, and provider/prompt changes are not applied to the server. Why: these need filesystem access. Workaround: use `pnpm app:dev`; browser mode is for UI work (or `VITE_OPAL_MOCK=1`).
- **Runtime — concurrency limit counts top-level prompts only.** `maxConcurrentConnections` gates prompts Opal sends; subagent (child) sessions the agent spawns and retries scheduled by OpenCode run inside their parent's slot and are not counted. Why: OpenCode starts them server-side. Workaround: lower the limit if a provider rate-limits subagent-heavy work.
- **Runtime — `sendPrompt` resolves on admission.** A prompt queued behind the limit keeps its promise pending until it gets a slot and the server accepts it (the optimistic user message shows immediately with activity `queued`). Why: errors at admission must reject the call. Workaround: callers clear the composer before awaiting (as `Composer` does).
- **Runtime — replayed message content.** `session.message.content.updated` (replay-only, untyped in @opencode/client 2.2.5) is handled by refetching that session's messages rather than patching in place, so a reconnect after a long gap can cost one full message reload per open session. Why: its payload shape is not part of the typed event union. Workaround: none needed; it is correct, only slower.
- **Runtime — orphaned sidecar after a hard kill.** SIGINT/SIGTERM/SIGHUP and normal quit stop the sidecar, but a SIGKILL of the app (or a crash) leaves `opencode serve` running until the next launch, which kills the PID recorded in `logs/opencode.pid`. Why: macOS has no parent-death signal. Workaround: relaunch Opal, or kill the PID in that file.
- **Runtime — free `opencode/*` models.** The bundled free models (public key) are rate-limited by the OpenCode service; `experimental.generate.text` (used by "Test connection") can fail with "Free usage limit reached" while normal prompts still work. Workaround: add your own provider key.
- **Runtime — edit/regenerate are destructive.** They use `session.revert.stage` + `revert.commit`, which deletes the reverted messages (and, on the Code surface, restores the tracked file changes); there is no branch history to switch back to. Why: OpenCode 2.2.5 has no message-tree/fork-at-message API. Workaround: duplicate the conversation first if the old answer matters.
- **Sandbox — reads, file tools and localhost are not confined.** The macOS sandbox (Settings → Security) limits _writes_ (and, in Strict mode, outbound network) of shell commands and Code terminals only. Commands can still read any file, the agent's own write/edit tools are governed by OpenCode permissions instead, and Strict mode still allows `localhost`. Why: `sandbox-exec` wraps the shell process; OpenCode's in-process tools cannot be wrapped without patching OpenCode. Workaround: keep Code permissions on "Ask"; see docs/SECURITY.md.
- **Sandbox — tools that write outside the working folder fail.** Global installs (`npm i -g`, `brew install`, `pip install --user`), `git config --global`, and tools that keep state in `~/.config` or `~/Library/Application Support` hit "Operation not permitted". Why: by design, only the working folder, temp and common package caches are writable. Workaround: add the folder under Settings → Security → Extra writable folders, or switch the sandbox off for that task.
- **Sandbox — `sandbox-exec` is deprecated by Apple.** It still works on current macOS, but Apple may remove it. If `/usr/bin/sandbox-exec` is missing, the wrapper runs plain `/bin/zsh` and Settings → Security shows that commands are unrestricted. Workaround: none needed today.
- **Sandbox — the Code terminal is sandboxed too.** The integrated terminal uses the same configured shell, so it is confined to the repository. Why: OpenCode uses one `shell` setting for agent commands and PTYs. Workaround: use Terminal.app for unrestricted work, or switch the sandbox off.
- **Remote control — LAN only, plain HTTP.** Paired devices connect over unencrypted HTTP on the local network; Opal does not open an internet tunnel. Why: OpenCode's tunnel (OpenTunnel) only runs in `opencode serve --service` mode, which takes its password from `service.json` instead of `OPENCODE_PASSWORD`, changes into `$HOME`, registers itself as the background service, and needs a separate `opencode service set remote true` to issue a device certificate (packages/cli/src/server-process.ts, services/remote-tunnel.ts). The tunnel also only routes to the engine port, not to Opal's web UI. Workaround for access away from home: install **Tailscale** on the Mac and the phone. Opal listens on every interface, including the Tailscale `100.x` address, so open the pairing link with its host replaced by the Mac's Tailscale IP (`http://100.x.y.z:47800/#rc=…`): the page always reaches the engine through the host it was loaded from, and the traffic is WireGuard-encrypted. Or use SSH port forwarding: `ssh -L 47800:127.0.0.1:47800 -L 47801:127.0.0.1:47801 you@mac`, turn off "Listen on the local network", and open `http://localhost:47800` on the remote computer. Never forward these ports on your router.
- **Remote control — pairing links use the first LAN address.** The QR code and link point at the Mac's primary IPv4 address (Wi-Fi/Ethernet first). Devices on another interface (Tailscale, a second network) need the link's host edited by hand (or use `http://<LocalHostName>.local:47800`, shown in Settings). If the Mac's address changes, Settings → Remote control shows "Your network changed" with a Refresh button that restarts the engine with the new addresses. Why: CORS origins are fixed when the engine starts.
- **Remote control — iOS home-screen app needs its own pairing.** A web app added to the iOS Home Screen does not share storage with Safari, so it starts unpaired. Workaround: in the home-screen app, paste a fresh pairing link (copy it from Settings → Remote control on the Mac) on the "Connect to Opal" screen.
- **Remote control — browser-mode features on paired devices.** The phone runs the browser build of Opal: settings, providers and prompt overrides are not synced from the Mac (it keeps its own local settings and uses the engine's default model), and there are no reveal/open/save-as file actions. Chats started on the phone do get a sandbox folder on the Mac (created through OpenCode's file API). Why: those features need Tauri on the device. Workaround: change settings on the Mac.
- **Remote control — dev mode serves the live Vite build.** In `pnpm app:dev` the LAN web server proxies the Vite dev server, so Vite's HMR websocket fails on remote devices (harmless console error, no hot reload). In release builds the bundled files are served.
- **Code surface — named worktree branches are made through the shell API.** OpenCode's `worktree.create` checks out a detached ref; Opal then runs `git switch -c <branch>` in the new worktree via `shell.create`. If that fails (e.g. the branch already exists), the session keeps the detached checkout and the badge shows the base ref. Why: OpenCode 2.2.5 has no "new branch" option. Workaround: pick a different branch name, or create the branch in the terminal.
- **Code surface — base branch is a ref, not a fresh fetch.** The base-branch picker passes the local ref to `git worktree add`; it does not fetch the remote first. Workaround: `git fetch` in the terminal before starting the session.
- **Code surface — working-tree diff refreshes on open, on switch and when the session goes idle.** There is no file watcher, so changes made in the terminal while the Diff tab is open need **Refresh**.
- **Code surface — terminals outlive their tab only by directory.** PTYs keep running on the server until their tab is closed; after a reload the Terminal tab re-attaches every running PTY in the session's directory (two sessions on the same local checkout therefore share terminals). PTYs whose worktree was removed keep running until closed. The terminal uses OpenCode's configured shell, so the sandbox setting applies to it.
- **Questions & forms — only session forms are shown.** The `question` tool and other OpenCode forms appear as a card above the composer in Chat and Code. MCP elicitations that OpenCode files under the `"global"` sentinel owner (not a real session) are not shown anywhere. Why: Opal lists forms per session (`session.form.list`). Workaround: none in Opal yet.
- **Questions & forms — external links count as done once opened.** For an `external` form field (e.g. a sign-in page), clicking **Open** marks it acknowledged; Opal cannot tell whether the step on that page was completed. Hidden fields are not rendered and send their default.
- **Questions & forms — Skip lets the agent continue.** **Skip** cancels the form with a short note ("The user skipped this question without answering."), which OpenCode returns to the model as tool feedback, so the turn continues. To end the turn instead, press Stop.
- **Code surface — browser build.** Reveal in Finder is unavailable, so the worktree chip copies the path; "Open folder…" asks for an absolute path with a prompt. Files and diffs are read through the OpenCode server API (512 KB viewer cap; binaries are not shown).
- **Code surface — mock terminal.** In `VITE_OPAL_MOCK=1` the terminal is a simulated line echo (pwd, ls, echo, git status), not a shell.
- **Acceptance smoke harness — not a pixel test.** `scripts/smoke-mac.sh` checks the preview's render status, its `artifact://` URL and that the HTML is real markup (not a placeholder); it does not screenshot or click inside the dashboard, and it approves any permission prompt once. Running the debug binary still writes Tauri's own per-user state outside `OPAL_HOME` (window position in `~/Library/Application Support/com.ditistijn.opal`, logs in `~/Library/Logs/com.ditistijn.opal`).
- **Artifacts — models can publish placeholders.** OpenCode's `artifact_create`/`artifact_update` store `files` verbatim. In the first automated run GLM-5.3 drafted the page in the working folder and published `{"index.html": "<<FILE:index.html>>"}`, so the preview showed that text and identical updates created no new version. The artifact prompt now says there is no file-reference syntax; Opal does not detect or repair a placeholder that a model still sends.
